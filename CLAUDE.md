# Ядро Minecraft-сервера

## О проекте

Мы разрабатываем новое ядро для Minecraft-серверов на Kotlin. Ядро — это **фреймворк**: оно подключается в проект, к нему добавляются библиотеки с готовыми системами (оружие, экономика и т.д.), и на их базе собирается конкретный игровой режим.

Предыдущее ядро было на базе Minestom и устарело. Новое пишется полностью с нуля, без Minestom.

## Ключевые принципы

- **Максимальная гибкость.** Никаких жёстких ограничений, всё должно быть переопределяемым.
- **Сложное ядро, простые реализации механик.** Мы готовы вложить сложность в ядро, чтобы разработчики геймплея писали максимально простой код.
- **Нет ванилы.** Мы не поддерживаем vanilla-механики Minecraft. Режимы — это перенос других игр в Minecraft (CS, GTA, билд-баттл, RPG и т.д.).
- **Слабая/средняя/высокая квалификация разработчиков.** У нас слоистая архитектура: разработчики уровней пишут декларативный код, разработчики систем — работают с ECS, разработчики ядра — с низкоуровневыми вещами.

## Слоистая архитектура

```
Уровни (контент)         — декларативный DSL, пишут слабые разработчики
   ↓
Геймплейные системы      — WeaponSystem, AbilitySystem и т.п., средние разработчики
   ↓
Базовые системы          — MovementSystem, DamageSystem, InventorySystem
   ↓
Платформенные системы    — InstanceSystem, ConnectionSystem, WorldSystem
   ↓
Protocol API             — абстракция над пакетами
   ↓
Реализации протокола     — адаптеры под конкретные версии
```

**Слои общаются через компоненты, а не через прямые вызовы.** Геймплейная система не "вызывает" платформенную, она ставит компонент (например `WantsToTeleport`), а платформенная система его обрабатывает.

## Instance — единица изоляции

**Instance** — это изолированный игровой контекст (сессия, матч, лобби, арена). Концептуально это актор:

- Собственное состояние, свой тик, свой ECS-мир
- Никто снаружи не лезет внутрь напрямую
- Между инстансами — только асинхронные сообщения
- Нельзя "перенести" entity между инстансами, только удалить из одного и создать в другом
- Потенциально может жить на другой машине (location transparency)

**Следствия, которые фиксируем с первого дня:**

1. **Нет глобального состояния.** Никаких синглтонов вроде `PlayerManager.getPlayer(uuid)`. Чтобы найти игрока — нужно знать, в каком Instance он сейчас.
2. **Между Instance — только ID и сериализуемые сообщения.** Никаких прямых ссылок на объекты из другого Instance.
3. **Все сообщения между Instance — `@Serializable`** (kotlinx.serialization). Даже если сейчас всё в одном процессе — пишем так, будто завтра будет по сети.
4. **Тики Instance независимы.** Один лагает — другие не страдают.
5. **Нет глобальной БД на уровне ядра.** Если Instance нужны сохранения — внутри него работает система, которая сама общается с БД асинхронно (через корутины).

**Lifecycle** — обычный Kotlin-код. Lobby-сервер в `main` создаёт лобби-инстанс, матч-сервер создаёт инстансы по запросу матчмейкера. Instance — это `AutoCloseable`, которым владеет создавший код.

## Connection vs Entity (критично!)

**В ядре нет класса Player.** Есть две разные концепции:

- **Connection** — TCP-сокет с клиентом, протокольное состояние. Живёт на gateway-слое, вне инстансов.
- **Entity внутри Instance** — обычная ECS entity с компонентами (например, `ControlledBy(connectionId)` и `RenderedTo(connectionId)`).

Связь между ними — через компоненты. Один connection теоретически может управлять несколькими entity. Когда connection отваливается — системы в инстансах узнают об этом и реагируют (по своему усмотрению: превратить в NPC, удалить, поставить на паузу).

**Почему это важно:** это радикально отличается от Bukkit/Spigot, где Player — это и сущность, и подключение. Наше разделение даёт чистоту, reconnect, спектатор-режимы, distributed-архитектуру.

## ECS — основа геймплейного слоя

Внутри Instance всё состояние живёт в ECS. Рекомендуемая библиотека для старта — **Fleks** (нативный Kotlin ECS с корутинами). Можно писать свой, но сначала стоит посмотреть на Fleks.

**Ключевые принципы ECS в нашем контексте:**

- **Data-only компоненты.** Компоненты — это `@Serializable data class`, без лямбд, ссылок на внешние ресурсы, `File`/`Socket`/`Thread`. Поведение — в системах, не в данных. Это нужно для будущей сериализации инстансов (реплеи, live-migration).
- **Системы запускаются в явном порядке внутри тика.** Никаких "приоритетов слушателей", никаких глобальных ивентов как основного механизма коммуникации.
- **Проблема порядка событий решается фазами внутри тика.** Пример: зелье лечит, проклятье дамажит. Решение — сначала все источники урона собираются, потом применяются модификаторы, потом суммируется урон/хил, потом проверяется смерть. Всё за один тик, детерминированно, не зависит от порядка регистрации.
- **Реактивность — через change detection в системах**, а не через подписки. Система каждый тик запрашивает "дай всех, у кого `Health` изменилось" и реагирует. Задержка в 1 тик для UI незаметна, архитектурно намного чище.

**Что решает ECS из наших текущих болей:**

- **Таксономия ("выкинутый предмет — это предмет или сущность?")** — больше нет. Есть entity с набором компонентов.
- **Модули на разных типах (Player, World, Arena, Item)** — больше нет. Есть компоненты, системы работают с теми entity, у которых нужный набор.
- **"Кто убивает, игрок или оружие?"** — решается явным контекстом урона: `DamageEvent { source, weapon, target, amount, type }`, который может модифицироваться системами.
- **Порядок обработки ивентов** — см. выше про фазы внутри тика.

## Система слоёв (Layer System)

Самая нетривиальная часть ядра. Нужна, чтобы нативно поддерживать:
- **Билд-баттл**: у каждого игрока свой холст на одних и тех же координатах, во время голосования все смотрят один холст.
- **Квартиры (GTA Online style)**: игрок в своей квартире видит улицу через окно, но снаружи квартира не видна, и у каждого игрока своя квартира на одном и том же месте.
- **Обычные арены**: один слой, все всех видят.

### Концепция

**Layer** — единица контента, содержащая блоки и/или entity. У каждого Layer есть:

- `id` — уникальный идентификатор внутри Instance
- `type` — **immutable** или **mutable** (формат хранения)
- `priority` — порядок наложения при конфликтах (выше приоритет = "сверху")
- `bounds` — ограничивающий объём для быстрого отсечения
- `voidMarker: BlockState?` — какой блок считать "явным воздухом" (дефолт `structure_void`, можно `null`)

**Immutable layer:**
- Хранится как обычные chunk sections с палитрами.
- Читается быстро, писать нельзя.
- Для заранее построенного контента: арены, карты, загружаемые из файлов.

**Mutable layer:**
- Хранится как разреженная структура (рекомендуется **sectioned sparse** — разреженный набор chunk sections, где каждая section — обычная палитра).
- Запись O(1), чтение чуть медленнее.
- Для динамического контента: квартиры, разрушаемые объекты, временные эффекты.

**Миграция типов:**
- `bake(mutable) → immutable` — когда слой стабилизировался (редко меняется).
- `unbake(immutable) → mutable` — если нужно начать активно менять.
- Это явные операции, не автоматика (автоматику можно добавить позже как оптимизацию).

### Подписки и видимость

У каждого entity-игрока есть компонент `LayerSubscription(layers: List<LayerId>)` — на какие слои он подписан. Видимость блоков и entity определяется пересечением "в каких слоях находится объект" и "на какие слои подписан наблюдатель".

Это покрывает все кейсы:
- **Билд-баттл**: каждый игрок подписан на `canvas_player_N`, во время голосования подписки переключаются.
- **Квартиры**: игрок подписан на `["street", "apt_vasya"]`, прохожий — только на `["street"]`. Прохожий не видит содержимое квартиры.
- **Обычная арена**: все подписаны на один слой.

Это **interest management через слои**. Дефолт — один слой `main`, все в нём. Сложные кейсы — кастомные слои.

### Семантика voidMarker

Чтобы слой мог "вырезать дыру" в нижестоящих слоях, в нём нужно записать блок-маркер "явного воздуха". По умолчанию это `structure_void` — удобно, потому что можно строить слои ванильным майнкрафтом через structure block.

Но `structure_void` может понадобиться как игровой блок в продвинутых режимах. Поэтому `voidMarker` — конфигурируемое поле:

```kotlin
// Дефолт: structure_void = явный воздух
val apartment = Layer.mutable("apt_vasya")

// Кастомный sentinel: structure_void используется как игровой блок,
// для дыр — barrier
val customLayer = Layer.mutable("custom") {
    voidMarker = Blocks.BARRIER
}

// Без sentinel: слой только добавляет, не может вырезать дыры
val decorations = Layer.mutable("decorations") {
    voidMarker = null
}
```

**Важное различие двух операций в mutable слое:**
- `remove(pos)` — "этот слой больше не определяет блок в этой точке, наследуй из нижестоящего"
- `put(pos, voidMarker)` — "этот слой определяет, что в этой точке воздух, не наследуй ничего"

### Композиция и рендеринг

Алгоритм получения итогового блока в точке:

```
для каждого слоя, на который подписан игрок, сверху вниз по приоритету:
    block = слой.get(pos)
    если block != null:
        если block == слой.voidMarker:
            результат = AIR
        иначе:
            результат = block
        break
иначе:
    результат = AIR
```

Замена `voidMarker → air` происходит **на этапе композиции**, не в отдельном финальном passe. Внутри ядра `voidMarker` — это честный блок с семантикой "явный воздух", снаружи клиент видит обычный `air`.

### Кэширование

- **Композиция immutable + immutable** — кэшируется агрессивно (пока существуют слои). Ключ кэша — упорядоченный набор layer id + координаты чанка.
- **Композиция с mutable** — кэшируется кратко (TTL) или инвалидируется при мутации mutable слоя.
- **Bounds слоёв** — для быстрого отсечения нерелевантных чанков при композиции.

### Мутации

Мутации происходят **в слое**, не в скомпонованном виде:
1. Геймплейная система решает, в какой слой писать (обычно через компонент `ActiveLayer(id)` на entity игрока).
2. Пишется блок в sparse structure слоя — O(1).
3. Инвалидируются кэши, где участвует этот слой.
4. Рассылается `BlockChange`/`MultiBlockChange` всем подписчикам слоя (с учётом перекрытия слоями выше по приоритету).

## Сериализация и live-migration

Одна из целей ядра — уметь **сериализовать Instance целиком** для:
- **Реплеев** (снепшотный стиль — периодические снепшоты состояния)
- **Live-migration** (пауза инстанса → перенос на другой сервер → продолжение)

**Что это требует от кода:**
- Все компоненты — `@Serializable` data classes
- Системы НЕ хранят состояние в полях класса — только локальные переменные в `tick()`. Если системе нужно помнить что-то между тиками — это компонент на singleton entity или resource
- Никаких ссылок на entity в Kotlin-смысле, только ID
- Никаких внешних ресурсов в компонентах
- Время — компонент/resource, не `System.currentTimeMillis()` напрямую

**Чего пока НЕ делаем:** детерминированные реплеи в стиле Starcraft (начальное состояние + ввод → проигрывание). Это требует полного детерминизма по всему стеку, что очень тяжело. Начинаем со снепшотного стиля, которого достаточно для live-migration и просмотра реплеев.

## Технический стек

- **Язык:** Kotlin
- **ECS:** рекомендуется Fleks (или своё, но сначала посмотреть на Fleks)
- **Сериализация:** kotlinx.serialization
- **Асинхронность:** Kotlin Coroutines + Channels (для I/O внутри систем, для актор-подобного общения между Instance)

## Открытые вопросы

Эти вопросы ещё не имеют финального ответа, и если код будет касаться их — нужно явно обсуждать с разработчиком, а не принимать решения самостоятельно.

1. **Освещение в композированных чанках.** Как эффективно считать свет для микса слоёв. Варианты: считать на финальном миксе с кэшированием, использовать свет базы и мириться с артефактами, гибрид. Решения пока нет.

2. **Smart resubscribe.** Когда у игрока меняются подписки на слои (зашёл в квартиру), как минимизировать количество пакетов и избежать мерцания. Нужно ли слать diff или полный resend.

3. **Физика и коллизии по персональному виду мира.** Игрок сталкивается с теми блоками, которые он видит, а не с "общим миром". Как это эффективно реализовать без копирования мира на каждого игрока. Идея — кэшировать collision view per-entity и инвалидировать при изменениях.

4. **Тики с разной частотой.** Нужны ли инстансам разные TPS (лобби 5, матч 20), или всегда 20? Не определились.

5. **DSL для разработчиков уровней.** Как выглядит код "уровня". Kotlin scripting, декларативные конфиги, обычный Kotlin с билдерами — не выбрано.

6. **Gateway архитектура для distributed-режима.** Где живут Connections, как проксируются пакеты между gateway и instance на другой машине. Концепция понятна, детали — нет.

7. **Глобальные сервисы (профили, статистика, экономика, чат между инстансами).** Архитектурно понятно, что это отдельные сервисы, общающиеся с инстансами асинхронно. Конкретика — открыта.

## Философские напоминания

- **Если добавляешь в ядро фичу — проверь, не можешь ли выразить её через существующие примитивы.** Хорошая архитектура — это когда абстракции стягиваются к меньшему числу концептов.
- **Events — не основной механизм коммуникации.** Если тянет сделать ивент — подумай, не лучше ли компонент + система.
- **Никаких неявных глобалов.** Если системе что-то нужно извне — оно приходит через зависимость или через компонент.
- **Простота для геймплейщика важнее элегантности ядра.** Если ядро некрасиво, но геймплейщик пишет одну строчку — это лучше, чем наоборот.
